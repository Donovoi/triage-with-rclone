# Synthetic Restart Manager calibration

This separate, ignored library test asks whether the reviewed Restart Manager adapter can report the current test process while it holds one synthetic file open, then report no applications after that handle closes. It does not run an application, rclone, an original removal operation, or a UI test. It cannot identify the cause of a historical sharing violation.

The existing manual `original-cleanup-trace.yml` gains a closed `mode` choice. `original_cleanup` is the default and retains its original steps and budgets. `resource_use_calibration` selects a separate hosted Windows ARM64 job. Both jobs check their mode with ordinal equality; the calibration also requires the exact dispatch commit, hosted ARM64 environment, and an explicit opt-in. The native test is ignored by ordinary suites.

The calibration creates one fresh directory directly under `RUNNER_TEMP` and one `synthetic.bin`. It writes fixed public bytes, explicitly closes the writer, then opens a read handle with READ/WRITE sharing and no DELETE sharing. Regular-file, link-count, content and identity checks bind that handle. The existing adapter stores the exact DOS path and caller PID/creation identity in memory; none of those identifiers is exported.

The first snapshot uses the unchanged adapter: closed identity probe, one Start, one registration of exactly this file and no process/service, one GetList with capacity 64, one End after a successful Start, and a closed final identity probe. The deliberate handle then closes exactly once. A second snapshot runs only if the first is available and that close succeeds. There is no retry or buffer-growth query. Calibration requires exactly one admitted application equal to the caller before close and zero applications afterward. Unsupported caller recall, an extra application, or a nonempty control remains unavailable.

After both snapshots, one final closed identity probe permits one `remove_file`; the retained directory handle closes explicitly, then one `remove_dir` removes only the empty owned directory. No recursive deletion, shutdown, restart, process inspection, kill or recovery loop is added. Unknown handle/session closure or identity prevents qualification and may retain the synthetic tree. No handle is held across an original application removal because this test performs no such removal. Identity brackets are not an atomic filesystem transaction, and the deliberately held directory handle remains present in both snapshots.

The synchronous RM calls have no hard deadline. The unchanged three-minute observation-step budget may terminate an incomplete test; that cannot produce a passing result or establish cleanup. There is no watchdog thread, abandoned worker, extra wait policy or hard-total-cleanup guarantee.

The native line is capped at 1024 bytes, including its prefix and newline. It contains only fixed scope/reason strings, booleans, numeric API statuses and bounded counts. The independent Python validator checks strict shapes, query/close order, both observations, cleanup conjunction, exactly one named ignored test and its actual exit. Its separate normalized artifact is capped at 8 KiB. Raw Cargo/test output remains private and is read with bounds after exit; those are not hard disk-growth caps. Output failure never creates calibration credit.

The workflow compiles a real ARM64 library-test artifact, selects it from Cargo JSON, hashes the harness and build record, and binds commit/tree plus a bounded tracked-source digest before and after execution. It also records the manifest and expected ARM64 rclone hash, **only as source/expected-runtime bindings**. It neither builds nor runs nor observes an application/rclone image. Only the normalized calibration report is uploaded.

This private proposal layers six files over the frozen RM supplement derived from PR112 `29266d15a4bda57408f2f8394a1698107d3fa4fe`. The original supplement has separate PR115 application-source references; this test does not borrow their execution or reassign their validator. Current-main reconciliation, review, an exact dispatch ref, ARM64 compilation/linking, Rust test execution and actual RM behavior remain pending. A later observation of the acquisition or menu failure requires its own explicit target and source binding.
